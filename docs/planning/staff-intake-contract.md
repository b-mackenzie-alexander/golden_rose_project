# Staff intake contract

**Status:** Finalized technical proposal for approved docs-only publication, 2026-09-14. Accepted conversational workflow direction is distinguished below from proposed implementation details. Activation requires the merged planning packet and merged improved-UI predecessor; not implemented or deployed and not independently client/counsel accepted.
**Authority:** ADR-0017 and `.hermes/plans/2026-09-14-staff-intake-workflows-plan.md`. Existing employer-demand contracts continue except for the precisely scoped intake additions here upon accepted publication. Until that acceptance, the new technical rules remain Proposed; docs-only approval does not activate code or runtime authority.

## 1. Outcome and acceptance boundary

Accepted direction: durable shared worker/employer intake drafts, explicit save/resume, version-checked changes, restricted addresses, current-version review, accountable follow-up, explicit existing-party links without overwrite, and complete/current-reviewed finalization by authorized staff. Self-review/finalization is allowed. Missing information stays absent. No public entry, automatic matching, verification, referral, placement, agreed compensation, messaging, uploads, OCR, geography vendor, live data or cloud operations follow from this contract.

Everything labeled a technical choice below is a **Proposed safe implementation choice**, not newly discovered client policy. These choices close drafting gaps for the private fictional-synthetic implementation; approved publication freezes them for implementation. Terminology, catalog contents, locale ergonomics, retention and named live access require later validation without blocking synthetic source work.

## 2. Aggregate and version semantics

`Intake` owns mutable candidate facts before finalization, not a second customer database. Fields: `intake_id` UUID, `kind` worker/employer immutable, `version` integer 1..2147483647, `content_version` positive integer, `lifecycle` draft/finalized, `created_at`, `updated_at`, `created_by`, `updated_by` (server attribution), typed content, nullable typed links. Reference is the full UUID; a shortened display token is not a lookup key. Localized “Unnamed intake” is never stored as a person's name.

Technical create floor: kind plus at least one nonempty substantive content field (not a link, system flag, empty array/object, `negotiable=false`, or null). Entirely empty drafts return 422; contact and name are not required. Every supplied value is validated. There is no timed autosave or browser persistence.

Every successful material command advances `version` by exactly one with a corresponding event; creation is 0→1. Content revisions and changed links also advance `content_version`. Reviews/follow-up advance aggregate version but not content version. Identical-content revision returns 409 `no_change` without write; identical command retries replay first. `reviewed_content_version`, exact `reviewed_record_version` and immutable `review_id` belong to the review record. A current review is the latest review disposition, is `intake_reviewed`, and covers the current content version and linked dependency versions. Follow-up bookkeeping alone need not invalidate content review, but a new `needs_follow_up` disposition supersedes it. Any candidate fact/link change invalidates current review. Nothing deletes old reviews.

Finalization submits current expected aggregate version and explicit latest `review_id`; locks recheck both, content version, completeness, linked canonical versions and permission. The reviewed record version can precede later follow-up bookkeeping; the reviewed **content** must be exactly current. This distinction is explicit in UI/history, never an assertion that a changed intake remains reviewed.

After finalization candidate content/links/review become immutable. Read/history remain; intake follow-up bookkeeping may continue with attributable events and without changing the finalized snapshot. No revise/relink/re-finalize with a new key. PR D in this outcome supplies the bounded canonical correction and current-facts re-review commands in §9. They never edit the intake snapshot or silently apply candidate differences. Do not fabricate a second identity to simulate correction. Broader lifecycle/reclassification/identity merging remains outside this outcome.

## 3. Typed fields, staged requiredness and purpose

All new DTOs forbid extra keys recursively, reject coercive booleans/numbers, use NFC/trimmed text, reject control characters, and omit unspecified fields; explicit null clears an optional draft field. Revisions are full replacements of the caller-authorized content sections, not merge patches; restricted sections use their own commands so omission cannot delete concealed data. API payload limit 32 KiB (413); lists max 50. Blank text is invalid, not a replacement name. UUIDs are full UUID values; expected versions are strict positive integers below the increment limit.

Technical shared value objects:
- `Address`: optional `line1` (1..200), `line2` (1..200), `locality` (1..100), `region` (1..100), `postal_code` (1..32), `country` (ISO 3166-1 alpha-2 uppercase, explicit selection; no implicit US). Draft components may be partial; review requires line1/locality/country and region/postal_code when country=US. Else region/postal optional. This is structural completeness, not address existence, deliverability, ownership, geographic eligibility or legal jurisdiction. Country catalog is pinned local data; no external address lookup.
- `Phone`: string 3..40, permits leading +, digits, spaces, parentheses, hyphen and explicit extension; 7..15 main digits, extension 1..6 digits. Preserve supplied display formatting after trim and derive a digits-only exact-match key internally. No guessed country prefix, carrier, messaging consent or E.164 assertion. Phone search is excluded in this outcome.
- `Offer`: optional components while drafting: `minimum`, `maximum` decimal strings (0..999999999.99, at most two fractional digits), `currency` ISO 4217 alphabetic code from pinned local list, `basis` hour/day/week/month/year/task, `per_worker` literal true, `negotiable` boolean default false. Review requires minimum/currency/basis/per_worker; maximum optional and >=minimum. Amount uses minimum alone; range uses minimum+maximum. Zero is structurally allowed and flagged for staff attention, not approved as lawful pay. No legal wage thresholds invented. `terms` optional 1..500, restricted detail only. Decimal arithmetic is exact; never float or locale-dependent transport.
- All narrative values are plain text, escaped on output, never rich HTML or unrestricted metadata. Duties/interests/follow-up are not protected-trait screening fields.

| Content section and owner before/after finalize | Save | Required for `intake_reviewed` and finalize | Classification / disclosure |
|---|---|---|---|
| Worker `full_name` (1..200) → Worker | Optional | Yes | PII; authorized name preview/search only |
| Worker `phone` → WorkerContact | Optional | Yes | Contact PII; detail only |
| Worker `residential_address` → WorkerResidence | Partial permitted | Complete Address | Restricted; purpose is staff intake completeness/follow-up, not travel or eligibility inference |
| Worker `interests` → WorkerPreferences: up to 20 `{interest_id, catalog_version}` plus `other_description` 1..200 | Optional | At least one active selection or Other description | Self-reported, unverified; detail only; no ranking/filter |
| Worker `availability` → WorkerPreferences | Optional/unknown | Explicit flexible or complete weekly ranges | Self-reported preference, not a shift commitment |
| Employer `employer_type` household/business and `display_name` 1..200 → new Employer | Optional | For a new Employer yes; for linked Employer resolve these from canonical row | Existing Employer creation requirements unchanged; no representative-name fallback |
| Employer `representative_name` 1..200 and `phone` → new EmployerContact + ContactDetails, or selected existing pair | Optional | Yes | Contact PII; separate from Employer identity |
| Employer `party_address` → EmployerAddress for business, ContactDetails address for household | Partial permitted | Complete Address of stated purpose | Restricted contact/business address, not worksite permission |
| Employer `worksite_address` → Worksite or explicit existing Worksite | Partial permitted | Complete Address | Restricted precise worksite |

| `follow_up` → IntakeFollowUpEvent | Not required for draft | Needs-follow-up: reason, owner, due instant mandatory | Shared responsibility; deadline not a private visibility partition |

Technical availability representation: `{mode: unknown|flexible|weekly, time_zone?, ranges?, exception_note?}`. Unknown is optional drafting only; flexible means “discuss with staff” and has no inferred days/ranges. Weekly requires explicit IANA timezone and 1..28 `{weekday:1..7, start_local:HH:MM, end_local:HH:MM, end_day_offset:0|1}`; end after start, duration >0 and <=24h, overlapping intervals rejected including week wrap. Overnight offset is explicit; no guessed overnight. Weekly preferences do not instantiate DST dates. A dated shift separately validates nonexistent/ambiguous local times and explicit offset. Flexible/unknown reject ranges; note <=500 optional and cannot substitute for a mode.

Technical demand schedule: `{mode: unknown|to_be_discussed|specified, requested_start_date?, starts_at?, ends_at?, time_zone?, note?}`. Specified requires either explicit ISO date-only requested start or all three timed fields; timed values are RFC3339 with offset, ends>starts, zone/offset consistent for both instants (reject gaps and mismatches). Date-only is not a timed shift. `to_be_discussed` rejects date/interval fields and means clarification remains outstanding even after intake review. Note <=500 cannot replace mode. **Finalization creates no ShiftNeed, even with a concrete schedule.** A later governed demand command must create the actual shift and satisfy request `draft→pending_review` child guard, shift `draft→pending_review` start/end/timezone/count guard, request required-for-open review, and parent-open guard for active shifts. No active demand/calendar timed shift/coverage comes from intake.

Technical work-interest catalog: `WorkInterest` with immutable UUID and code, versioned bilingual labels (1..100), active/retired, actor/time. Owner or separately delegated Manager maintains entries; Operations Staff cannot govern the catalog. No business categories are invented as accepted: initial synthetic fixtures use conspicuously fictional categories; real catalog validation remains pilot discovery. Other is a UI option stored as description, not an automatically published category. Retired selections stay readable historically; review requires replace/explicitly choose active selections, without rewriting the old review.

Same-address control copies current values once into the distinct destination candidate section, after source/destination field authorization. Later edits never propagate. Existing canonical records selected as sources are **references**, not copied editable customer masters.

## 4. Permission matrix (new identifiers, not deployed grants)

All actions also require actor and record scope. Business role labels alone do not authorize. Synthetic principals and revocation fixtures exercise these rights; existing develop synthetic identity is not a named RBAC rollout. Do not add a real identity provider, directory, user-management UI or grants in this outcome.

| Exact permission | Owner | Authorized Manager | Operations Staff | Platform Administrator |
|---|---|---|---|---|
| `intake:read`, `intake:draft:create`, `intake:draft:revise`, `intake:link`, `intake:follow_up` | Allow | Allow | Allow | Deny |
| `intake:review`, `intake:finalize` | Allow | Explicit delegation each | Explicit delegation each | Deny |
| `worker:read`, `worker_contact:read`, `worksite:read`, `staffing_request:read`, `employer_contact:details:read` | Allow | Allow | Allow | Deny |
| `worker_residence:read`, `worker_residence:write`, `party_address:read`, `party_address:write`, `worksite_address:read`, `worksite_address:write` | Restricted each | Restricted each | Restricted each | Deny |
| `intake:restricted_history:read` | Restricted | Restricted | Restricted | Deny |
| `work_interest:read` | Allow | Allow | Allow | Deny |
| `work_interest:manage` | Allow | Explicit delegation | Deny | Deny |

`intake:review` does not grant `intake:finalize` automatically: same eligible role scope, distinct explicitly checked actions. Needs-follow-up review requires `intake:review` and `intake:follow_up`; baseline follow-up lets staff reschedule/reassign/log an existing follow-up but not mark reviewed. Draft save requires neither. Worker review/finalize also requires worker residence read; employer review/finalize requires party/worksite address read; creating new canonical restricted fields additionally requires their write permissions. Linking requires canonical read rights for selected targets plus existing `employer:read`/`employer_contact:read` prerequisites. Existing Employer create/read/search/revise and contact routes retain their current permissions and DTOs. Finalize is a separately approved orchestrator capability to create its listed outputs, not a generic bypass into all canonical create/correction APIs.

Existing ordinary request/shift review remains **Allow for Operations Staff** under its original matrix. Intake does not revoke or inherit that right. Precise worker residence/party-address rights do not imply precise-worksite/calendar reveal or vice versa. Authorized intake detail can reveal only the separately authorized section; broad rows never carry precise fields. Capture of a restricted field requires both read and write so a staff user can inspect what they submit. No concealed-field round-trip replacement.

Reviewer/owner names come from an injected trusted staff directory abstraction, never request body. Synthetic fixture directory has stable UUIDs, display names, active/record-scope membership and permission sets. Owner assignment validates an active staff member with intake read/follow-up scope; reassignment reason is mandatory. Production identity/delegation authority and named recipients remain gated.

## 5. Canonical outputs and linking ownership

Explicit links are optional in incomplete drafts and are version checked. Party selection never auto-merges by name/phone/address. No silent update of selected records or partial creation during linking. A link dependency has `{id, version}` and the intake preserves expected versions for review/finalization; missing/out-of-scope target is 404, changed target 409. A canonical Employer edit after link invalidates review at read/finalize time even if intake content did not change; staff refresh links explicitly, compare and re-review.

| Finalization case | Exact output set and authority |
|---|---|
| New worker | One Worker (`full_name`, version=1, staff attribution); one WorkerContact (`worker_id`, phone); one WorkerResidence (`worker_id`, Address); one WorkerPreferences (`worker_id`, interests+availability, self_reported=true); typed authority/events for each; finalization result references all four. |
| Existing worker linked | Reuse Worker plus its current WorkerContact, WorkerResidence, WorkerPreferences IDs/versions; create no new worker profile children and overwrite none. Review completeness is evaluated on the referenced canonical facts. Candidate differences stay in protected intake history and are flagged for an explicit §9 canonical correction, not silently considered applied. If existing children are absent/incomplete, finalization is blocked (409 `canonical_incomplete`), not patched by intake. Missing child creation is not a correction endpoint. |
| New employer | One existing-shape draft Employer with explicit type/name, source staff_entry; one EmployerContact with name and version=1; one new versioned ContactDetails (phone; household contact Address if household); business also one EmployerAddress (purpose business); one Worksite; one StaffingRequest in draft, linked by same-employer FKs to contact/worksite and business address where applicable. No ShiftNeed/coverage/zone/map assignment. |
| Existing employer linked | Reuse Employer and its type/name. Explicitly reuse complete contact+ContactDetails or create a new pair, and reuse Worksite or create new Worksite. Business explicitly reuses a complete EmployerAddress or creates a new one; household address belongs to selected/new ContactDetails. Always create **one new draft StaffingRequest** for the new need; never overwrite/reopen an existing request. Reuse of selected contact/worksite/address must belong to the same Employer. Selected rows are read-only; a create-vs-reuse choice is explicit and reviewed. |

Technical identity minimum for new Worker is nonblank name, but no canonical create action is exposed at that minimum: all review-required worker fields must be complete/current-reviewed before the atomic group is created. Existing Employer constraints (nonblank name, type, draft lifecycle, staff_entry) and EmployerContact version=1 remain untouched. Phone/address live in new one-to-one `employer_contact_details` keyed to contact, not by relaxing the legacy contact row or expanding its old DTO. Existing legacy contacts without details remain usable by the old API, but cannot be reused as a complete intake contact. No details-upsert endpoint is introduced. PR D adds separate version-checked details corrections under §9; deliberate creation of a different contact must never be presented as correcting the old contact. The legacy EmployerContact row and its original DTO remain unchanged; current representative corrections belong to versioned ContactDetails.

Finalization produces an immutable `IntakeFinalization` row unique on intake ID and an exact typed `FinalizationOutputs` representation. Worker variant: worker/contact/residence/preferences `{id,version,disposition:created|reused}`. Employer variant: employer/contact/contact_details/worksite/request references and nullable business_address reference with the same shape; request always created. All refs have concrete FKs, parent-scoped composite FKs where needed, stored original versions and `kind` shape check; no JSON-only output IDs. Intake ID, command ID, review ID and finalized content version bind the row to one operation. Canonical current read endpoints—not snapshots—own subsequent detail. The finalization row owns historical created/reused links.

Historical intake retains submitted/reviewed facts; ordinary get of a linked draft resolves selected canonical fields and shows a version mismatch flag rather than overlaying candidate values onto canonical truth. `candidate` and `resolved` sections are named distinctly in detail. New fields always remain candidate until finalize. Historical snapshot of reviewed restricted sections is stored only in protected review payload tables. Intake is never a synchronization source after finalize.

## 6. Exact new HTTP contract

Prefix `/api/staff/v1`; static query routes registered before UUID routes and verified against path capture. All command POSTs require `Content-Type: application/json` and `Idempotency-Key: <UUID>` using existing dependency; unknown/malformed keys →422. Mutation bodies contain no command/actor/time IDs. No `If-Match` or ETag concurrency alias: use `expected_version` explicitly. New routes do not change old Employer or contact responses.

Named DTOs (all strict, unknown keys forbidden):
- `CreateIntakeRequest {kind, content: WorkerDraftContent|EmployerDraftContent}`. Restricted address sections may be supplied only with required section rights. Response `IntakeCommandResponse`.
- `ReviseIntakeRequest {expected_version, content}` replaces non-address candidate sections only. `ReviseIntakeAddressRequest {expected_version, address: Address|null}` replaces exactly one route-selected address. Unsupported kind/section →422. Every address edit advances content/version and invalidates review.
- `QueryIntakesRequest {kind, lifecycle: draft|finalized = draft, name_query?:2..100, reference?:UUID, page_size:1..50=25, cursor?:string<=1024}`. Name and reference mutually exclusive. No query means a bounded shared kind-specific draft list, not an unbounded dump. No owner-private filter, counts, phone/address/traits/availability filters.
- `LinkIntakeRequest {expected_version, party: {id,version}|null, contact?:{id,version}|null, worksite?:{id,version}|null, business_address?:{id,version}|null}`. Worker party resolves all child refs server-side; employer sublinks require party; null unlinks dependents explicitly. Linking returns resolved metadata only, never unrequested restricted fields. Existing/new contact/worksite modes are derived from nullable explicit links; UI requires deliberate choice before review.
- `ReviewIntakeRequest {expected_version, outcome:intake_reviewed|needs_follow_up, note?:1..512, reason_code?:missing_information|clarification|other, reason_text?:1..512, owner_staff_id?:UUID, next_follow_up_at?:RFC3339, time_zone?:IANA}`. Needs-follow-up requires code, nonblank reason_text, owner, due instant and zone; reviewed rejects follow-up fields. Current review requires completeness; needs-follow-up permits incomplete facts. Same authorized actor may review and finalize.
- `FollowUpIntakeRequest {expected_version, action:reschedule|reassign|attempt, reason_text:1..512, owner_staff_id, next_follow_up_at, time_zone, method?:phone|email|in_person|other, outcome?:no_answer|voicemail_left|callback_requested|contact_reached_information_pending|invalid_contact_information|information_received|other, note?:1..512}`. Existing follow-up required; all commands retain a due instant and active owner; attempt additionally requires method/outcome. Date may be past deliberately (shows overdue), no arbitrary future-only rule. An attempt records staff-reported contact, sends nothing, does not auto-mark reviewed or close.
- `FinalizeIntakeRequest {expected_version, review_id:UUID}`. No new values in finalization; all material choices must already be reviewed.
- `IntakeSummary {intake_id,kind,version,lifecycle,display_name?:string,complete:boolean,missing_fields:string[],review_status:unreviewed|needs_follow_up|current|stale,updated_at,follow_up?:{owner_staff_id,next_follow_up_at,overdue},offer?:OfferSummary}`. Missing fields are allowlisted field codes, no values; name absent stays absent. OfferSummary contains only min/max/currency/basis/per_worker/negotiable. Owner labels require trusted directory lookup.
- `IntakeDetail {summary,content_version,candidate:<non-address content>,resolved:<non-address selected canonical content>,links:<typed refs>,dependency_stale:boolean,latest_review?:{review_id,reviewed_record_version,reviewed_content_version,outcome,actor_id,actor_display_name,occurred_at},finalization?:FinalizationOutputs}`. Never emits raw addresses, phone search keys, protected notes or snapshots. Phone and narrative supplied content are authorized detail fields only, not summaries.
- `IntakeAddressDetail {intake_id,version,section:worker_residence|party_address|worksite_address,candidate:Address|null,resolved:Address|null,source_ref?:{id,version}}` returned only with section read. Missing values and permission denial are distinct: 403 is not an empty address.
- `IntakeCommandResponse {command_id,result_record_version,current:IntakeDetail,finalization?:FinalizationOutputs}`. Replay returns original result version/output IDs plus current authorized minimized detail, whose version must be >=result version. No historical sensitive response replay. Missing current authority or receipt integrity is 503, not fabricated success.
- `IntakeHistoryPage {items:[{event_id,version,content_version,event_type,actor_id,actor_display_name,occurred_at,review_id?,outcome?,owner_staff_id?,next_follow_up_at?}],next_cursor}`. Restricted note/review values fetched individually through protected history endpoint; ordinary audit changed_fields stores field names only.

- POST `/workers/query`: `{name_query?:2..100,reference?:UUID,page_size=25,cursor?}`; exactly one identifying filter required, page max50 → `{items:[{worker_id,full_name,version}],next_cursor}` under worker:read. Both require employer:read+party_address:read; list never includes address values.
- POST `/employers/{employer_id}/worksites/query` → bounded `{items:[{worksite_id,employer_id,version}],next_cursor}`; GET `/employers/{employer_id}/worksites/{worksite_id}` → same identity plus `location_verification_status:supplied`, `service_area_status:unassigned`, `map_area_status:pending`; GET same path + `/address` → identity+Address. worksite:read+employer:read; address requires worksite_address:read.
- POST `/employers/{employer_id}/requests/query` → bounded `{items:[{staffing_request_id,employer_id,version,request_status:draft,role_title,worker_count,offer:OfferSummary}],next_cursor}`; GET `/employers/{employer_id}/requests/{request_id}` → same plus contact/worksite/business-address IDs, duties, schedule, offer including terms, request_type household/general_labor, created/received/updated timestamps, source_channel staff_entry. staffing_request:read+employer:read. No address values.
- POST `/work-interests/query` → `{page_size=25,cursor?,include_retired:false}` → bounded `{items:[{interest_id,code,version,label_en,label_es,active}],next_cursor}` under work_interest:read. POST `/work-interests` → `{code:1..64 [a-z0-9_],label_en,label_es}`; POST `/work-interests/{interest_id}/revisions` → `{expected_version,label_en,label_es,active}`. Manage permission, Idempotency-Key, command outcome `{command_id,result_record_version,current:<interest>}`, 201 create/200 replay or revision. Codes unique immutable; no delete.

All bounded canonical parent queries use `{page_size:1..50=25,cursor?:<=1024}` unless specified. Cursor is integrity-protected, opaque, versioned and bound to kind/parent/filter/record-scope identity/page size and order; reuse with changed authority or filters fails 422. Stable keyset order `(created_at DESC,id DESC)` for draft/canonical lists, `(version DESC,event_id DESC)` for history; no total counts. Name match uses normalized literal fragment (escape SQL wildcards), not fuzzy or identity evidence. No names in URL querystrings. Read authorization occurs before query or cursor decoding; field authorization before sensitive projection. Authorized record miss and out-of-scope IDs share 404; missing action permission 403 without lookup.

Transport rules for **every new response including routing/auth/validation/unexpected errors**: `Cache-Control: no-store`, `Vary: Authorization`, `X-Content-Type-Options: nosniff`; success `Content-Type: application/json`, errors `application/problem+json`. Mutation successes add `Idempotency-Replayed: true|false` and `Idempotency-Result-Version: <integer>`; first creates/finalizations add `Location` for the created intake or `/intakes/{id}` (finalization), catalog creates for catalog resource. Replays do not emit Location. No ETag, Last-Modified, reflected body, SQL or sensitive URL in errors. New errors `{type:urn:golden-rose:intake:<code>,title,status,detail:<fixed safe phrase>,code,missing_fields?:<allowlisted codes>}`; codes 401 unauthenticated, 403 forbidden, 404 not_found, 405 method_not_allowed, 409 version_conflict|idempotency_conflict|review_required|dependency_changed|already_finalized|canonical_incomplete|no_change, 413 payload_too_large, 415 unsupported_media_type, 422 invalid_request|incomplete|invalid_cursor, 503 persistence_unavailable. Authorized completeness response alone may include missing_fields. Never raw Pydantic `input`/`ctx`. 503 `Retry-After: 1`; it does not promise the write failed—browser retains original command identity and exact submitted payload until resolved. Disallow unsupported methods explicitly; API unknown paths must not fall through SPA HTML. Preserve old API problem contracts.

## 7. Persistence, receipts and transaction strategy

Observed source at a6f0791: only Employer/contact typed authority; command_receipts has one primary result per command; audit_events reverse-FKs every event to that same primary result. Existing services commit. Merely adding several audits under one finalize command is **not possible** under that bijection. Technical migration below is mandatory; never relax to unconstrained UUIDs or compose committing services.

New tables:
- `intakes`: base metadata, version/content_version/lifecycle, kind-discriminated bounded JSONB candidate non-address content (schema_version=1 with recursive API validation; DB checks top-level key allowlist/kind and size); nullable worker_id/employer_id with kind-exclusive concrete FKs and expected versions. JSONB is not generic metadata. Normalized `intake_addresses` holds `(intake_id,section)` primary key, partial Address columns; per-section type/kind check. `intake_links` stores nullable contact/worksite/business-address concrete FKs and expected versions, with same-employer composite constraints.
